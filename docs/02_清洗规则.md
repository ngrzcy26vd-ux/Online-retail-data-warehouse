## 0. 数据源与规模

- 数据集：UCI Online Retail，541,909 行 × 8 列
- 字段：InvoiceNo / StockCode / Description / Quantity / InvoiceDate / UnitPrice / CustomerID / Country
- **关键事实：没有 status 字段**——订单状态无法直接判断，「哪些是取消单」靠 **InvoiceNo 前缀**识别：数字=正常交易、C=Cancel 取消、A=Adjust 财务调整

## 1. 数据画像结果（六维）

| 维度 | 数量 | 发现条件 | 为什么这个条件能发现它 |
|---|---|---|---|
| 负数量 | 10,624 | `Quantity < 0` | 零售业务里数量为负只有退货/取消一种合法解释，异常度极高 |
| 取消单 | 9,288 | `InvoiceNo` 以 C 开头 | C = Credit 贷记单，会计惯例，红字冲销 |
| 客户缺失 | 135,080（24.9%） | `CustomerID` 为空 | 散客现场交易不留客户 ID |
| 零单价 | 2,515 | `UnitPrice == 0` | 赠品/搭赠合法存在，异常度不够高，只配当**证据**不当**发现条件** |
| 完全重复行 | 5,268 | `duplicated()` | 八列全同，人工重复录入（99.2% 带完整 CustomerID，判据硬） |
| 非商品编码 | 约 2,900（任务书旧数 2,396 待复核） | 白名单逐条核对 | 字母码多为费用类，但 DCGS/gift/PADS 字母开头也是真商品，不能正则一刀切 |

> 方法论：发现异常用「不可能正常」的高异常度条件（数量为负、单据号带字母、整行全同）；单价=0 不够异常，只在交叉验证时当证据。

## 2. 单据四分类规则

| 类别 | 判定条件 | 行数 |
|---|---|---|
| 正常单 | 非C 且 非库存 且 非坏账 | 531,282 |
| 取消单 | `InvoiceNo` 以 C 开头 | 9,288 |
| 库存盘点记录 | 负数量 且 非C | 1,336 |
| 坏账调整 | `StockCode='B'`（= InvoiceNo 以 A 开头，全库仅 3 行，描述 Adjust bad debt，数量 +1、单价 ±11,062.06） | 3 |

**闭合验证**：531,282 + 9,288 + 1,336 + 3 = 541,909 ✓

**三维度交叉验证**：InvoiceNo 首字符（数字/C/A）× UnitPrice 是否为 0 × CustomerID 缺失率，三个独立维度指向同一划分，分界线零矛盾：
- 取消单（C 开头）9,288 行单价全部 ≠ 0
- 库存记录（负数量非C）1,336 行单价全部 = 0
- 坏账（B 码）3 行是全库唯一负单价行（另 1 行为计提的正单价）

**C = Credit（贷记）**：会计惯例——取消单/退货单用**负数单据冲抵原单**，而不是删除原单。好处是保留审计痕迹：账面始终能追溯「哪一笔被冲抵、冲了多少」，查账时原单还在。

**负数量的业务含义分两种，不能一句话归成取消单**：
- **C 开头的负数量（9,288 行）= 取消/退货**——客户侧行为，货退了或单撤了
- **非 C 的负数量（1,336 行）= 库存盘点调整**——仓库侧行为，破损、丢失、盘亏，不是客户取消

四分类就是按这个切的。区分它们的意义：取消单要冲 GMV，库存记录根本不进 GMV（没有真实销售）。

## 3. 三个字段代码（单价=0 集合的二分）

```python
cond_cancel = df["InvoiceNo"].str.startswith("C")
cond_stock  = (df["Quantity"] < 0) & ~cond_cancel
cond_bad    = df["StockCode"] == "B"
cond_zero_price = (df["UnitPrice"] == 0) & ~cond_stock
```

- `is_stock_record` = `df[cond_stock]` → **1,336**
- `is_zero_price` = `df[cond_zero_price]` → **1,179**（补集：单价=0 全集 − 库存）
- 验收：1,336 + 1,179 = 2,515 = 单价=0 全集 ✓，互斥 ✓

**「条件等价 ≠ 定义等价」**：is_stock_record 加不加 `UnitPrice==0` 在当前数据同数（负数量非C 的 1,336 行恰好全部单价=0），但定义上必须以单价=0 为前提——全集是单价0 的 2,515 行。`~cond_stock` 让 pandas 做德摩根，人不展开，避免手滑。

## 4. CustomerID 缺失的分层处理

- 规则：**订单层保留、用户层排除**；清洗时填 `UNKNOWN`（不填 0，0 会变成假客户）
- 缺失行占 GMV 25%（= 缺失 CustomerID 行的金额合计 ÷ 全表金额合计，分子分母都只在该子集内算）

**为什么分层（不是「有的有、有的没有所以分开处理」，是「指标粒度决定数据要求」）**：

- **订单层指标（GMV、订单数）只问「交易有没有发生」**，不要求知道是谁——CustomerID 缺失的行照样参与，全删会凭空丢掉 25% 的 GMV
- **用户层指标（复购率、留存、RFM）必须定位到「是不是同一个人」**，CustomerID 缺失的行做不到，只能排除；填「未知客户」更糟——所有散客会被算成 1 个大客户，用户层指标全错

原则：**在指标口径允许的范围内尽可能小地影响数值**——三个选项（全删 / 填充 / 分层）里，分层是唯一不丢订单数、不造假用户的。

## 5. GMV 口径体系

- **净额为主口径：9,758,809.99**（退货自动冲减）；毛额辅助：10,655,622.48；取消冲抵占毛额 **8.42%**
- 四口径矩阵（每个口径登记用途，下游按用途取）：

| 口径 | 定义 | 用途 |
|---|---|---|
| 净额 × 含客 | 冲减后，含未识别客户 | **主口径**：GMV 总量 |
| 净额 × 无客 | 冲减后，仅识别客户 | 用户层指标（复购/留存） |
| 毛额 × 含客 | 不冲减，含未识别客户 | 销售规模上限 |
| 毛额 × 无客 | 不冲减，仅识别客户 | 参考 |

- 口径差异近一成，**不声明则下游必然用错**——这是「口径治理」的核心理念

【你写】→ 已由本人补写（11-11）：

三个口径是「越来越真」的三层：

- **GMV（成交总额）**：全部成交金额，是**意向**——包含后续被取消、被退货的单。毛额口径不挑单，全部相加
- **净销售额**：正常单 + 取消单冲抵之后，是**成交**——货真价壮出去了、没退的那部分
- **Revenue（真实收入）**：在净额基础上再剔除非商品收入（运费、手续费不是卖货赚的），是**纯赚**

本项目主口径：GMV 净额 9,758,809.99。口径选错的影响：取消冲抵占毛额 8.42%，近一成的差异——下游用错口径，所有分析结论跟着偏。

## 7. 清洗动作清单（周四/周五对账基准）

| 问题 | 动作 | 验收数 |
|---|---|---|
| 完全重复行 5,268 | **删**（`drop_duplicates(keep="first")`，删第 2 次及以后） | 541,909 → **536,641** |
| 取消单 | 保留（净额口径下自动冲抵，不单独删） | 9,288 |
| 库存记录 | 保留 + 标记（不进用户层指标） | 1,336 |
| 坏账 3 行 | 保留 + 标记（同时是非商品，剔出 GMV） | 3 |
| 零单价（赠品） | 保留（订单层计 GMV；104 行正数量库存动作词归此类，见第 8 节） | 1,179 |
| CustomerID 缺失 | 分层：订单层保留、用户层排除；清洗填 `UNKNOWN` | 135,080 |
| 非商品编码 | 剔出 GMV，单列 | 白名单核对后定 |
| 格式脏值（编码空格/大小写、Description 空格、EIRE） | 归一：TRIM + 大写 + 类型转换，**不删行** | 行数不变 536,641；Description 唯一值 4,210 → 4,195 |

**「不删行、只置 NULL」原则的沿用边界**：字段级问题（脏值/格式/缺失）一律置值不删行；**行级问题（整行八列完全重复）删行**——重复行无任何信息量，保留只会污染计数。两个层级，两套处理，不矛盾。

**删除安全性证据**：被删的 5,268 行中 CustomerID 缺失仅 43 行（0.8%）——99.2% 带完整客户 ID，「同客户同分钟同商品同数量同价」八列全撞，必是重复录入。按类型分布：正常单 5,231 / 取消单 37 / 库存 0 / 坏账 0——**系统生成的单从不重复，重复是人工流程的病**。

【你写】→ 已由本人补写（11-11），归一五步，每步的「为什么」：

1. **编码列 TRIM + 转大写**：洗掉 `m` / `M` 这类大小写脏值。不统一的直接后果是 `is_cancel` 漏判——`c536534` 不以 C 开头，会被当成正常单
2. **Description 去空格 + 填「未知商品」**：前后带空格的有 113,453 条，不 TRIM 按类目汇总会把同一类拆成多类；缺失填「未知商品」让空值可见、可追溯
3. **CustomerID 转 `Int64` 再转字符串**：float 的 `17850.0` 直接转会变成 `"17850.0"`，distinct 计数时同一个客户被拆成两个；必须用 `Int64` 而不是 `int64`——有 NaN，普通整型装不了
4. **EIRE → Ireland**：同一国家两种写法（旧称/现称），按国家汇总会被拆成两行
5. **预计算 line_amount**：`quantity × unit_price` 先乘完再 `round(2)`——下游不用反复乘，且避免每步 round 累积误差

**环境注意事项**：CSV 的 UTF-8 BOM 已移除——Hive 不认 BOM，列名会变成 `\ufeffInvoiceNo` 导致 SQL 静默查空（不报错、返回空结果）。

3. **归一未制造新重复**：归一后 `duplicated().sum()` = 0，数据形态变化未产生新的完全重复行
