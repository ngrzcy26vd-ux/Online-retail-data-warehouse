## 二、数据本身的坑（15 条）

### 金额类：影响数值大小

| 坑 | 规模 | 后果 |
|---|---|---|
| `UnitPrice = 0` | 2,510 行 | 金额算 0，GMV 低估。其中商品口径 1,157 行是真正的赠品 |
| `UnitPrice < 0` | **2 行**（−11,062.06） | 坏账冲销，直接减收入 |
| 坏账 3 行里 1 行是**正数** | +11,062.06 | 用「负单价」定义坏账会漏掉它，净额多减一倍 |
| `Quantity` 极端值 | 5 行，最大 80,995 | **总额无影响**（两对正负抵销），但平均订单金额被拉爆 |
| 604 张纯费用单 | 金额 −330,261.53 | 必须在 GMV 之外，但单不能丢 |

### 计数类：影响订单数、客户数

| 坑 | 规模 | 后果 |
|---|---|---|
| 整行完全重复 | 5,268 行 | 所有 count 指标偏大 |
| `CustomerID` 缺失 | 135,080 行（**24.93%**） | `value_counts()` 默认隐藏，会以为没缺失 |
| `CustomerID` 填 0 的诱惑 | — | 会造出「最大客户」，Top-N 榜单第一永远是它 |
| 取消单混入 | 9,251 行 / 3,836 单 | 被算进销售额则收入虚高 |

### 维度类：**金额一分不差，但分组全错**（最阴的一类）

| 坑 | 规模 | 后果 |
|---|---|---|
| `StockCode` 大小写重复 | **112 个编码**，1,977 行含小写 | `85123A`(2,301) 与 `85123a`(67) 是同一商品，Top-N 榜错位 |
| `Country` 多写法 | `EIRE` 8,184 行 | 爱尔兰被拆成两行 |
| `Description` 前后空格 | 112,371 行 | 同一商品名被分成两类 |
| `Description` 占位符 | `?` 47 行、`??` 7 行 | 汇总时多出一个叫 `?` 的商品 |
| `Description` 缺失 | 1,454 行 | 归一后唯一值 4,223 → **4,195** |

### 格式类：影响能不能跑通

| 坑 | 表现 | 后果 |
|---|---|---|
| CSV 带 **UTF-8 BOM** | 文件头前 3 字节 `ef bb bf` | Hive 列名变 `\ufeffinvoice_no`，SQL **静默查空** |
| `InvoiceDate` 是 **object** | 不是 datetime | 任何时间运算都报错，必须 `to_datetime` |
| `CustomerID` 是 **float64** | 显示 `17850.0` | 同一个客户被拆成两个；`replace("NA")` 匹配不上 |
| 32 个非标准编码 | 2,989 行 | 其中 **15 个是费用类**（2,940 行）、17 个是**真商品**（49 行） |

## 三、代码的坑：**4 个静默失败**

这四个都**不报错**，全靠对数字才能发现。

### 1. `isin()` 用错列（代价最大）

```python
df2["is_non_product"] = df2["Description"].isin(FEE) | ...   # ❌ 列用错
df2["is_non_product"] = df2["StockCode"].isin(FEE)   | ...   # ✅
```

`Description` 里是 `POSTAGE`，`FEE` 里是 `POST`，`isin` 永远为假。
语法合法、类型合法、结果全 False —— pandas 不觉得有问题。
**后果：多算进 38 万费用，毛额 10,630,362.93 看着像个正常数字。**

> 定位方法：**差额反推**。差的 685.81 正好等于 GIFT 五档合计 → 说明 `startswith` 生效、`isin` 没生效。

### 2. `rename` key 对不上就静默跳过

```python
.rename(columns={"invoiceNO": "invoice_no"})   # ❌ 实际是 InvoiceNo
```

找不到列就跳过，不报错。**而后续代码若正好用了旧列名，还会"碰巧跑通"——错得更深。**

### 3. `astype("int64")` 遇 NaN 直接抛异常

```python
.astype("int64")                              # ❌ Cannot convert non-finite values
.astype("Int64").astype(str).replace("<NA>","UNKNOWN")   # ✅
```

`astype(str)` 之后缺失值是 `"<NA>"` 不是 `"NA"`，`replace` 匹配不上。

### 4. 临时变量 ≠ 表里的列

```python
doc_type = pd.Series("正常", index=df.index)   # 独立对象
df2 = df.drop_duplicates().copy()              # 复制的是 df，doc_type 不跟着走
```

分类算出来了，但只活在内存里。**想让结果长期可用，必须显式 `df["xxx"] = ...` 写进表。**

### 附带一个：列名凭记忆手写

犯过三种：`coustomer_id`（拼错）、`items_lines`（复数）、`invoiceNO`（大小写）。

> **列名属于"必须从输出复制、不能记忆"的东西。**

## 四、认知的坑（比技术坑更贵）

| 错误认知 | 正确认知 |
|---|---|
| 「罕见 = 异常」 | **异常 = 符合业务定义但罕见**。`Description="?"` 极罕见但它是**脏**（占位符伪装）；`Country="EIRE"` 出现 8 千次但也是**脏** |
| 「跑通 = 对」 | 退出代码 0 只说明没报错。**不 print 验收等于没验收** |
| 「55 万行 = 55 万笔交易」 | 一行是**商品明细**，只有 2.59 万张单 |
| 「负数量 = 取消单」 | 10,587 行负数 = 取消 9,251 + **库存 1,336**。这个说法会被面试一问就穿 |
| 「改了列名 = 生效了」 | `rename` 找不到就静默跳过 |
| 「分类算过了 = 存下来了」 | 临时 Series 不进表 |
| 「数字不用记，知道方向就行」 | 方向来自数字。**不查极值，就想不到「平均订单金额不能用」** |

## 五、方法论（能带走的）

### 1. 三类偏差方向 —— 拿到任何新表都先问这三句

| 方向 | 问什么 | 后果 |
|---|---|---|
| **数值偏大/偏小** | 有零值、负值、极值吗？ | 毁金额、均值 |
| **计数多算/少算** | 有重复、缺失、状态标记吗？ | 毁订单数、客户数 |
| **实体被拆开** | 有大小写、空格、多种写法吗？ | **毁分组、Top-N，金额完全不受影响** |

> **清洗不是为了金额对，是为了维度对。**

### 2. 先查询后删除

删不可逆、查免费。**先 `duplicated()` 看分布，再 `drop_duplicates()`。**

这次查出来的分布非常有说服力：

```
正常  5,231     ← 人工录入
取消     37     ← 人工操作
库存      0     ← 系统生成
坏账      0     ← 系统生成
```

> **系统生成的单从不重复，重复是人工流程的病。** 有了这个证据才敢删——万一系统单据也重复，那是数据同步问题，删了就毁证据。

### 3. 差额反推诊断

不要盯着代码猜。**先把差额算出来，再去找哪个东西的金额正好等于这个差额。**
这次差的 685.81 → 精确等于 GIFT 五档合计 → 直接指向"`startswith` 生效、`isin` 没生效"。

### 4. 每建一列就打印一次数量

```python
df2["is_non_product"] = ...
print(df2["is_non_product"].sum())   # 必须 2940
```

**这是对付静默失败的唯一通用防御。** 数量级不对就是错了。

### 5. 一层只从上一层聚合，不跳层

`明细 → 订单 → 客户`。跳层会让 `count` 的语义悄悄变（行数 vs 单数），而 `count` 永远不会告诉你。

### 6. 报数字时主语必须完整

| ❌ 含糊 | ✅ 完整 |
|---|---|
| 取消单 3,836 | **取消单的笔数** 3,836（对应 9,251 **行**） |
| 负单价 2 行 | **单价为负的有** 2 行（坏账共 3 行） |
| 库存 1,336 | **库存记录行数** 1,336（对应金额 0.00） |

**每次数字对不上，几乎都不是算错，是主语边界没对齐。**

### 7. 一章一步，一次只验一处

三处一起改，错起来没法定位。**先只改 rename，`print(columns)` 确认，再改下一步。**

## 六、关键判断的依据（面试会被追问的）

| 判断 | 依据 |
|---|---|
| 库存记录 = 数量<0 且非 C | **三个证据同时成立**：单价 100% 为 0（无资金流动）、客户 100% 为空（不挂客户）、描述写着 `Damaged`/`Thrown Away`/`Check` |
| 费用类用**穷举白名单**而非规则式 | DCGS(45 行)、PADS(4 行) 编码格式也不规矩，但看描述和价格是真商品。规则式会误杀，GMV 少 398.45 |
| 坏账 = `StockCode='B'` 而非负单价 | 3 行里 1 行是 +11,062.06（冲回）。**标记回答"什么业务"，符号回答"钱往哪走"，两者独立** |
| 用户层排除 UNKNOWN | 否则做出"0 号客户是最大客户"的假结论。排除后差额 1,505,841.23 可精确解释 |
| 两个 GMV 口径 | 结构完全同构，**同一批行、同一个金额列，只差一个 `\| is_cancel`**。这是可解释性的来源 |

## 七、如果我重做一遍，会改什么

1. **读数据时就定类型**：`dtype={"CustomerID":"Int64","InvoiceNo":str,"StockCode":str}`，省掉后面一串转换和坑
2. **去重放在归一之后**：先把 `"85123a"` 和 `"85123A"` 统一，再判重——这次的重复是按原始格式判的，可能有"归一后才暴露"的重复
3. **一开始就建 `doc_type` 字符串列并写进表**，而不是用临时 Series
4. **每个派生列建完立刻 print**，不等最后金额对不上才回头查
5. **所有验收数字写在一张纸上，标明所属阶段**（原始 / 去重 / 订单层 / 用户层）——今天在"行数 vs 单数"上绕了三次
